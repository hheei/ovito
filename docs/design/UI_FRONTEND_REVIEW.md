# Qt Quick Frontend vs. the Classic Frontend — Difference Review & Abstraction Proposals

> **Companion documents**: [UI_DESIGN.md](UI_DESIGN.md), [UI_PLAN.md](UI_PLAN.md), [UI_PHASE0_AUDIT.md](UI_PHASE0_AUDIT.md), [UI_PHASE1_SPIKE.md](UI_PHASE1_SPIKE.md), [UI_TEST_ENV.md](UI_TEST_ENV.md)
>
> **Status**: Review only. Nothing in this document is implemented; the proposals are ordered by the phase in which
> they would pay off. Measurements were taken on the Linux/OpenGL host described in UI_TEST_ENV.md unless noted.

This document answers one question: **where does the new Qt Quick workbench differ from the classic QtWidgets
frontend, and which of those differences should be removed by a shared abstraction before more UI is built on top?**

It complements the plan (which schedules *what* to build) by looking at *how* the two frontends do the same job and
where the same responsibility currently exists twice.

---

## 1. Method and scope

The two frontends were compared surface by surface, by reading the code and, where a claim is about runtime
behaviour, by measuring it:

| Frontend | Files | Lines |
| --- | --- | --- |
| `src/ovito/gui/base` (shared: actions, models, viewport input, BaseViewportWindow) | 43 | ~8 100 |
| `src/ovito/gui/desktop` (classic QtWidgets frontend) | 255 | ~36 900 |
| `src/ovito/gui/qml` (Qt Quick workbench, incl. the spike) | 28 | ~5 400 |

Everything below is grouped into four kinds of difference, because they need different treatment:

* **(A) Same behaviour** — implemented in both frontends with the same semantics. Nothing to do.
* **(B) Different semantics** — implemented in both, but the QML frontend behaves differently. Each of these needs an
  explicit decision: align, document as a deviation, or make the classic side follow the better behaviour.
* **(C) Not implemented yet** — either scheduled in UI_PLAN.md or deliberately out of scope. Listed to keep the
  remaining parity gap honest and measurable.
* **(D) Duplicated responsibility** — the same job is implemented twice, in two frontends or as two core entry
  points. These are the abstraction opportunities (§4).

## 2. (A) Already equivalent

Worth stating, because these are the load-bearing parts and they are shared, not re-implemented:

* **Scene rendering** — the frame graph, `StandardRenderer`/`StandardRendererImplementation` and OVITO's own shaders
  are used unchanged from the QML viewport; only the QRhi instance differs (Qt Quick's instead of `RenderThread`'s).
  The shared pass sequence now lives in `FrameGraphRenderPass` (core/rendering), used by both frontends.
* **Viewport layout semantics** — pane rectangles and handles are derived from the real
  `ViewportConfiguration::layoutRootCell()` tree, so the QML pane order matches the classic frontend (Top/Left |
  Front/Perspective); a splitter drag is one undoable `"Resize viewports"` transaction and maximize is non-undoable,
  exactly as in `ViewportsPanel`.
* **Undo/redo** — `UndoStack` + `UndoableTransaction` from core; no frontend-side undo bookkeeping.
* **Input modes** — `ViewportInputManager`, `NavigationModes`, `SelectionMode` and the `BaseViewportWindow` event
  handlers from gui/base are reused; the QML item only forwards Qt Quick events into them.
* **Import path** — one implementation in `WorkbenchUI::importFiles()` (gui/base) with the same
  `ResetScene`/`AddToScene` decision, cancellation cleanup and undo-stack reset.
* **Auto-key mode, task registration, error routing** — `WorkbenchUI` (gui/base).
* **Viewport overlays, orientation tripod, viewport titles, construction grid** — generated by core
  (`ViewportWindow`), i.e. identical; the grid is off by default in *both* frontends (it is a viewport-menu toggle).

## 3. (B) Same feature, different behaviour

### 3.1 Object picking: blocking vs. asynchronous

| | Classic | Qt Quick |
| --- | --- | --- |
| API | `ViewportWindow::pick()` blocks the GUI thread on `RenderTarget::requestPick()` | `pick()` answers from a cached `ObjectPickingBuffer` and starts a background refresh (at most one in flight) |
| Hover cost | one picking render + ~10 MB readback **per mouse move** (SelectionMode picks on every move) | zero while the scene does not change; one refresh after a camera move, result is one frame stale |
| Staleness | never | one refresh (documented deviation) |

A picking pass costs 20–150 ms per pick on this host (measured on the QML path: 110–150 ms for the first pick, which
includes creating `RenderThread` and its QRhi, and ~23–25 ms once warm). The classic frontend performs that work
synchronously inside the mouse-move handler, so the QML policy is the better one and the right fix is **not** to make
QML behave like the classic frontend, but to give both frontends one asynchronous pick API (§4, A3).

### 3.2 Frame rate and idleness

Both frontends render **on demand**: measured on the product (`ovito --gui=qml`, empty scene, Xvfb) the process burned
**0 CPU ticks in 6 s** while idle, and core only requests a frame when something changed
(`ViewportWindow::requestRerender()`), exactly as for the classic window.

The high frame rates reported for the QML spike (100–175 fps) are *load* numbers: the harness deliberately requests a
new frame per rendered frame (`spike/Main.cpp`, `measureFrameRate()`, "measures the frame rate the viewports achieve
when frames are requested continuously, which is what animation playback does"). The classic frontend cannot exceed
the display refresh because its swap chain is vsync-limited, so the comparable claim is "both sustain the display
refresh; the QML frontend has headroom above it".

Consequence for design: a "skip unchanged frames" optimization is **not** needed and should not be reintroduced later
without a measurement that shows re-rendering while idle.

### 3.3 Import options

The classic frontend asks: per-file `FileImporterEditor` inspection, wildcard/sequence handling, and a modal
import-mode dialog (`AddToScene`/`ReplaceSelected`/`ResetScene`). The QML frontend imports with fixed defaults
(`ResetScene`, auto-detected format, `ImportAsTrajectory`) and reports only success/failure. The *difference is
silent* — a `.xyz` file that autodetects as "LAMMPS Data" (see F6 in UI_PHASE1_SPIKE.md) simply loads an empty scene.

Recommendation: keep the simple path, but make it *visible* (log the detected format and frame count into the status
line) until §4/A6 provides the option model.

### 3.4 Status bar, tasks and errors

| | Classic | Qt Quick |
| --- | --- | --- |
| Task progress | `TaskDisplayWidget`: one progress bar **per running task**, cancellable individually | single task text + progress + Cancel (the first running task) |
| Errors | collected in `MainWindow::_errorList`, shown as a modal list with details, plus first line in the status bar | first line in the status bar, rest in a modal QML dialog |
| Message boxes | blocking `QMessageBox`, animation playback stopped | blocking nested event loop on a QML dialog (same semantics, documented in UI_PHASE0_AUDIT.md D20) |

Multiple concurrent tasks already occur (pipeline evaluation + offscreen render + import), so the QML status bar
should be fed by a shared task model rather than by `visitRunningTasks()` formatting in each frontend (§4, A5).

### 3.5 Per-viewport UI

The classic frontend's per-viewport UI is the `ViewportMenu` context menu (gui/desktop/viewport/ViewportMenu.cpp):
Preview Mode, Show Grid, Constrain Rotation, View Type (Top/Bottom/Front/Back/Left/Right/Ortho/Perspective),
Adjust View…, Window Layout (Split Horizontal/Vertical, Remove Viewport), Pipeline Visibility, Create Camera.

The QML viewport currently has **no context menu at all**: `BaseViewportWindow::mousePressEvent()` forwards a
right-click to `ViewportInputManager::requestContextMenu()`, whose signal has no receiver in the QML frontend, so
right-click does nothing. This is the most visible UX gap of the current shell and it also blocks the "insert/delete
viewport" work that UI_PLAN.md deferred to Phase 4.

### 3.6 Session, settings and window state

* Session (`defaults.ovito`, session save/open, recent files): classic only (`GuiApplication::initializeUserInterface`,
  `RecentFilesList`).
* Persisted UI settings: both use core's `ViewportSettings` for the viewport layout/maximized viewport; window
  geometry, renderer name, recent directories and the theme are QtWidgets/`QSettings`-side in the classic frontend and
  not persisted at all in QML.
* Window title: equivalent (derived from the data set/session path), implemented twice.

### 3.7 Not exactly comparable

* **Menu bar**: the classic frontend is menu-driven; the QML shell is a toolbar/button-driven workbench. This is a
  deliberate design difference (UI_DESIGN.md), but it means every command needs a second presentation anyway — which is
  why the command layer (§4, A1) matters more for QML than a menu port would.
* **Multiple viewport windows / secondary windows**: classic supports detached viewport windows; QML has a single
  window (not scheduled).
* **macOS specifics**: the classic frontend relies on `QAction` menu roles for the native menu bar; the QML shell has
  no menu bar, so About/Quit/Preferences are not reachable through the system menu yet.

## 4. (D) Duplicated responsibility — the abstraction proposals

Ordered by priority. "Evidence" names the two implementations that currently duplicate the job.

### A1 — Frontend-neutral command layer (P1, ~1–2 days) — **implemented**

**Status.** Implemented as decision D26 of [UI_PHASE0_AUDIT.md](UI_PHASE0_AUDIT.md): `gui/base/actions/Command.h`
holds the neutral command, `ActionManager` owns the commands and mirrors them onto their `QAction` views, the 65
creation and 36 `QAction::triggered` call sites were converted, `ViewportModeAction` survives as a thin `QAction` view
of a `ViewportModeCommand` for the eight widget-based consumers, and the QML workbench binds its shortcuts and state to
the same objects (verified by the spike's `--qml-command-check`). Still to do as part of the later phases: the QML
menu bar and the pipeline/panel commands that currently live in the desktop command panel, and the icons (A9).

**Evidence.** 76 action ids are declared centrally (`gui/base/actions/Actions.h`), and **51 of the 65
`createCommandAction(...)` call sites are already in gui/base** — only 14 are desktop-only (command-panel pages,
snippet import/export, overlay-layer operations, modifier templates). So the *command surface is not the problem*; the
problem is its representation:

* `ActionManager`, `ViewportModeAction` and the models that a UI is supposed to consume
  (`PipelineListModel`, `AvailableModifiersModel`, `AvailableOverlaysModel`) hand out **`QAction*`** (QtWidgets), and
  `GuiQml` links `GuiBase` and therefore QtWidgets transitively.
* `gui/qml` references **0** `ACTION_*` ids: the QML frontend re-implements the handful of commands it has
  (undo/redo, maximize, import) instead of reusing 51 existing definitions.

**Proposal.** Introduce a frontend-neutral command description in gui/base — id, text, shortcut(s), checkable,
checked/enabled/visible state, trigger — with:

* `ActionManager` (desktop) becoming the QtWidgets *adapter* that keeps the existing `QAction`s, shortcuts and menu
  roles (no behaviour change for the classic frontend);
* a QML-exposed list/QAbstractListModel in `GuiQml` mapping commands to `MenuItem`/`ToolButton`/`Shortcut`
  (shortcut strings via `QKeySequence::toString()`).

**Payoff.** Every command is implemented once, has one shortcut table and one enabled-state rule; the command palette
planned for later phases gets its data for free; the QML module can eventually drop its QtWidgets dependency.

**What was measured.** The QML process sees 43 commands of the 76 action ids through the command layer (the rest come
from the desktop command panel, which the QML frontend does not have yet, and from the pipeline item commands of
`PipelineListModel`). The QtWidgets side is unaffected: `getAction()` still returns the `QAction` for menu/toolbar
insertion, and the 36 handler connects were re-targeted without a signature change.

### A2 — Viewport window management (P1, ~2–3 days)

**Evidence.** Per-viewport window lifecycle exists twice:
`ViewportsPanel::createViewportWindows()` / `setInteractiveViewportRendererForAllWindows()` /
`fatalViewportWindowError()` (with revert-to-default-renderer and re-creation retry) vs.
`QmlViewportController` + `QmlViewportLayout` + `QuickViewportItem` (item creation per pane, renderer assignment,
item replacement rules, hide/show resource release).

**Proposal.** A `ViewportWindowManager` in gui/base that owns, for a `ViewportConfiguration`: creation/destruction of
one window object per viewport (through a small `ViewportWindowFactory` interface), assignment of the interactive
`SceneRenderer`, recovery when window creation fails, active-viewport/maximize bookkeeping, and the mapping between
layout cells and window objects. Desktop implements it with `QWidget` containers, QML with `QuickViewportItem`s.

**Payoff.** The trickiest frontend rules (renderer assignment before first frame graph, resource release on hide,
never destroying a window from within a QML callback) live in one place instead of two.

### A3 — One asynchronous pick API (P1, ~2–4 days, touches core)

**Evidence.** This fork already added the asynchronous ingredients in core: `ObjectPickingBuffer`
(core/rendering/ObjectPickingBuffer.h), `RenderThread::renderPickingFrame()` and
`ObjectPickingMap::lookupPickResult()`. The QML frontend uses them; the classic frontend still blocks the GUI thread
in `RenderTarget::requestPick()` from `WidgetViewportWindow::pick()`, and the pick policies (radius, staleness,
buffer-size validation) are implemented separately in both frontends.

**Proposal.** Turn `ViewportWindow::pick()` into a thin wrapper over an asynchronous `pickAsync()` (returning a future
or delivering via a callback) and move the "which buffer is current / refresh when stale / validate geometry" policy
next to `ObjectPickingBuffer` in core. `SelectionMode`, `NavigationModes` and `XFormModes` then consume the async path
in both frontends; the classic blocking behaviour can be kept temporarily as a synchronous wait *on top of* the same
code path, if changing classic behaviour is not acceptable yet.

**Payoff.** Removes the classic frontend's per-hover-move stall and ends the second picking implementation.

### A4 — Offscreen rendering service (P1–P2, ~1–2 days)

**Evidence.** Three consumers drive `RenderThread` themselves, each with its own lifetime and flag handling:

* `RenderSettings.cpp:272,378` (render output) — `createOffscreenTarget(size * supersampling)` + `renderOffscreenFrame`
* `WidgetViewportWindow.cpp:216,220` (`grabViewportImage`) — offscreen target + render + CPU readback
* `QuickViewportWindow.cpp:276,282` (picking) — `createOffscreenTarget(size, forPickingOnly)` + `renderPickingFrame`

with four near-identical entry points (`createOffscreenTarget`, `renderOffscreenFrame`, `renderAOFrame`,
`renderPickingFrame`) whose misuse is asserted at runtime rather than prevented by types.

**Proposal.** One core-facing service ("render this frame graph offscreen and give me an image / picking buffers / AO
samples") that owns target creation, supersampling, readback and reuse, plus a shared `PickingBufferTarget`. The QML
render output planned for Phase 7 and the classic render output would then use identical code.

### A5 — Workbench state models (P2, ~2–3 days)

**Evidence.** Presentation state is computed twice: the classic frontend spreads it over `TaskDisplayWidget`,
`RecentFilesList`, `MainWindow` (window title, status bar, error list) and `QSettings`; the QML frontend recomputes
tasks, title, empty state, status line and message boxes in `QmlWorkbenchController` + `QmlMainWindowUI`.

**Proposal.** Move the *data* (not the widgets) into gui/base QObjects: a task/progress model fed from
`UserInterface::taskProgressBegin/End` and `visitRunningTasks()`, a selection/hover model, a recent-files model, a
small application-settings facade, and a session service. Two skins render the same model.

**Payoff.** The classic frontend's per-task progress bars and cancellation become available to QML without a second
implementation, and the "no session support" gap (3.6) becomes a matter of binding, not of new logic.

### A6 — Import plan / options model (P2, ~1–2 days)

**Evidence.** `WorkbenchUI` already owns the import flow, but the *decisions* it makes default silently
(`determineImportMode`, `inspectImporterFiles`, wildcard resolution). The classic frontend overrides these hooks with
`FileImporterEditor` inspection and a modal import-mode dialog; QML overrides nothing.

**Proposal.** Represent the pending import as an observable "import plan" (per-URL format, detected frames, chosen
mode, validation warnings) in gui/base. Desktop presents it with the existing dialogs, QML with a small form; a
frontend without UI can accept defaults but *log* them.

### A7 — Property model foundation (P2, before Phase 6, ~3–5 days)

**Evidence.** The property system is already QML-friendly: `PropertyField::getQVariant()`/`setQVariant()`
(core/oo/PropertyField.h:128,143) map every property type, including `Color` → `QColor` and enums → `int`. But the
editor infrastructure is entirely desktop-side (64 files in `gui/desktop/properties`, incl. `PropertiesPanel`,
`PropertiesEditor`, `DefaultPropertiesEditor` and dozens of specialized editors) and the knowledge encoded there —
units, min/max, "resettable", animation-controller references, sub-object editors — is exactly what the QML inspector
must reproduce (UI_DESIGN.md already commits to units/bounds/controller semantics in Phase 3–6).

**Proposal.** Build the frontend-neutral part first: property *field* enumeration per object kind, plus an editor
registry keyed by property descriptor/type producing an entry model (label, type, value, unit, range, read-only,
resettable, animated). Desktop keeps `PropertiesPanel` as one rendering of that model; QML gets a second.

**Payoff.** Prevents the largest single duplication of the migration; without it, Phases 4 and 6 will re-derive these
rules in QML.

### A8 — Remaining core/frontend couplings (P3, small, independent)

| # | Coupling | Where | Suggested cleanup |
| --- | --- | --- | --- |
| A8.1 | `StandardRenderer` still includes `RenderThread.h` to call the statics `pickGraphicsApi()`, `enumerateAdapters()`, `selectedAdapterName()` | core/rendering/standard/StandardRenderer.cpp | move to `RendererService` or a small graphics-API utility; completes the RendererService extraction |
| A8.2 | Application services look up the main window: `dynamic_object_cast<MainWindowUI>` | `NewGraphicsSystemService`, `UpdateNotificationService` (guarded since Phase 1) | a GUI-neutral "notify/confirm with details" interface next to `UserInterface::showMessageBox()` |
| A8.3 | `--noviewports` is a desktop-registered option read by core | core/dataset/DataSet.cpp:54 | treat "no viewports" as a core command-line parameter, or let the frontend decide the default viewport configuration |
| A8.4 | The `ovitoheadless` QPA plugin does not exist in the tree (O1) | core/app/StandaloneApplication.cpp | either ship the minimal plugin or print a clear error and require an explicit `QT_QPA_PLATFORM` |
| A8.5 | `QAction` usage in gui/base's "shared" models | ActionManager (view only, state lives in `Command`), PipelineListModel (commands), AvailableModifiersModel/AvailableOverlaysModel (still `QAction`) | largely resolved by A1 - the remaining `QAction`s are views created by `ActionManager::actionView()`, so a QML frontend does not need them; the two availability models still register plain `QAction`s and should follow |

### A9 — Icons and theme assets (P3, ~1 day)

The classic frontend ships two icon themes (`gui/base/resources/icons/ovito-dark|light`, SVG, with a common
`CommandIcon`-style tinting in the desktop widgets). The QML shell draws its own glyphs (the maximize button is made
of `Rectangle`s). Sharing the SVG set and the tint rule keeps toolbar/menu/command-palette visuals identical across
frontends instead of inventing a second icon language.

## 5. (C) Not implemented yet — the parity gap as of this review

Scheduled in UI_PLAN.md (phases 3–7): pipeline list (the model already exists in gui/base and needs only a QML
wrapper), parameter inspector + specialized editors, timeline/keyframes/animation, render settings and render output,
data inspector, command panel / modifier library, viewport toolbar with view modes and zoom actions, viewport
insert/delete and the rest of `ViewportMenu`, `AdjustView` and render-preview mode, snippet import/export, settings
dialogs, Python console (when the Python plugin is built).

Deliberately out of scope (documented in UI_DESIGN.md/UI_PLAN.md): menu-bar-driven workflow, multiple windows,
session files (until A5), plugin-specific dialogs, and the desktop's widget-based property editors.

Not previously listed anywhere, and worth an explicit decision:

* right-click context menu in the viewport (3.5) — currently a no-op;
* undo/redo discoverability (shortcuts exist, no menu item/tooltip);
* per-task progress display (3.4);
* "About"/"Quit"/"Preferences" reachability on macOS (3.7).

## 6. Optimization opportunities

Done in earlier rounds (kept here for the record, with the measured effect):

| Change | Effect |
| --- | --- |
| One `RendererService` per window instead of one per viewport item (UI_PHASE0_AUDIT.md D23) | 64.0 → 114.0 fps at 512 atoms (threaded loop), 118.0 → 175.5 fps (basic loop), +15 % at 32 768 atoms |
| Shared `FrameGraphRenderPass` (D24) | one implementation of the frame-graph pass sequence instead of two |
| Layout model updates objects in place (D25/F12) | no QML delegate rebuilds on drag/resize/maximize; assert-only defect fixed |
| On-demand rendering | verified: idle CPU is 0 (3.2) |

Open candidates, each with the measurement that must decide it:

1. **Single "viewport canvas" item** — four `QQuickRhiItem`s mean four offscreen color textures, four
   `beginPass/endPass`, four synchronize steps and four composites per window frame. One item rendering all panes in
   one pass (panes are already laid out in C++ by `QmlViewportLayout`) would share one resource frame and one pass.
   *Measure first*: compare frame time at 512/32 768 atoms; the earlier per-item resource work (D23) suggests a
   further win is plausible but the remaining fixed cost is now smaller.
2. **Picking pre-warm** — refresh the picking buffer when the camera or scene changes instead of after the next hover
   pick, removing the documented one-frame staleness. Cost: one picking pass per camera change (the classic frontend
   already pays this per hover).
3. **Frame-graph generation cost** — each window frame generates one frame graph per pane (unavoidable: four
   cameras), sharing the vis cache (already shared). Profile with the spike's `--qml-frame-stats` before optimizing.
4. **Launcher/`--gui` UX** — an unknown frontend name currently prints the available names and exits 1; a typo in a
   desktop file therefore produces a console error only.
5. **Not recommended**: merging the four panes into one viewport render call (the classic frontend draws four times
   as well), and "skip unchanged frames" (see 3.2 — nothing renders while idle).

---

## 7. Recommended order

1. **Before Phase 3 UI work**: A1 (command layer, **done**) and A5 (state models) — they determine how much of every
   later feature has to be written twice. A1 landed first so that the pipeline view and the inspectors of Phase 4 can
   bind to commands instead of creating a second command table.
2. **Together with the pipeline/property work (Phase 4)**: A2 (viewport window management) and A7 (property model).
3. **With Phases 5–7**: A3 (async picking), A4 (offscreen rendering service), A6 (import options).
4. **As independent small chores**: A8.1–A8.5, A9, plus the four small gaps listed at the end of §5.
